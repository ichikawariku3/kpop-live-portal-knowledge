# 表示速度 計測レポート（2026-11-15）

対象：kpopliveinjapan.com（トップ／ライブ一覧／YESUNG記事）
方針：実サイトは変更せず、計測と改善案の文書化のみ。

## 計測方法と制約

- 本来は Google PageSpeed Insights API で計測する予定だったが、キーなし公開エンドポイントのクォータ上限（429 Quota exceeded）に当たったため、**Performance スコア／LCP／CLS／INP の実測値は取得できなかった**。
- 代替として curl で各ページの HTML・読み込みリソース（script／style／img の本数とサイズ、TTFB、gzip 後サイズ、画像の実寸）を実測した。数値はこの計測環境（海外経由）からの参考値で、国内ユーザーの体感とは差がありうる。
- スコア系の指標が必要になったら、後日 pagespeed.web.dev で手動確認するか、API キーを用意して再計測すること。

## 良い状態だった点

- HTML は gzip 圧縮が効いており、転送量は 31〜40 KB に収まっている。
- SWELL が CSS をインライン展開しており、外部CSSの待ちがほぼない。
- 画像の遅延読み込み（lazysizes）が一覧・記事で機能している。
- TTFB は中央値で 0.7 秒前後。ConoHa のキャッシュ（X-Nginx-Cache）が効いた状態では実用範囲。

## 気になった点

1. **ロゴが過大**：2560×800・318 KB の PNG を高さ36pxで表示。全ページ共通で読むため、無駄が全PVに効く。
2. **ヒーロー画像が重い**：796 KB の JPEG。トップの表示体感（LCP）に直結する。
3. **カード画像の配信サイズが表示サイズより大きい**：1024px 幅で配信し、実際はその半分以下で表示。一覧ページ総量 4.5 MB の主因。
4. **静的アセットに明示的なキャッシュヘッダが見当たらない**：画像・JS の HEAD 確認で cache-control／expires が付いていなかった（経由プロキシの影響はありうるため要再確認）。再訪時の読み込みが毎回発生している可能性がある。
5. **gtag.js が約535 KB**（HEAD の content-length 実測）：GA4 計測に必要なものなので削除対象ではないが、全ページ共通の固定費として認識しておく。

## 改善案（運用範囲内・優先順）

### 優先1：ロゴ画像の軽量化
- 内容：ロゴを実表示サイズ（高さ36px、Retina想定でも幅 600px 程度）にリサイズし、WebP 化する。318 KB → 数十KB 以下が見込み。
- 効果：全ページ・全PVで効く。特にモバイルの初期表示。
- 手間・リスク：小。カスタマイザーでロゴ画像を差し替えるだけ。透過PNGの見た目が変わらないよう、変換後の画質確認だけ必要。

### 優先2：ヒーロー画像の WebP 化
- 内容：`hero-a-brand-glow.jpg`（796 KB）を WebP に変換して差し替える（絵柄は同一、形式のみ変更）。見込みは 200 KB 前後まで削減。
- 効果：トップページの LCP 改善に直結。トップ総量の約2割減。
- 手間・リスク：小〜中。SWELL のメインビジュアル設定で画像を差し替えるだけだが、差し替え後に複数幅での実描画確認が必要（デザイン変更時の通常フローどおり）。

### 優先3：カード画像の配信サイズ見直し
- 内容：ライブ一覧とスライダーで配信されるサムネイルを 1024px 幅から 768px（または表示実寸に近いサイズ）に下げる。SWELL のサムネイルサイズ設定／画像サイズの選択で対応できる範囲を確認する。
- 効果：一覧ページの画像総量 4.5 MB → 4〜5割減が見込み。スクロール時の追随も軽くなる。
- 手間・リスク：中。既存画像の再生成（Regenerate 系）が絡む場合は全記事分に及ぶため、まず設定箇所と影響範囲の確認から。画質劣化が目立たないか実描画チェック必須。

### 優先4：静的アセットのブラウザキャッシュ確認
- 内容：画像・JS・CSS に長期キャッシュ（cache-control）が付くよう、ConoHa WING 側の設定と .htaccess の現状を確認する。CSS/JS は ver パラメータ付きなので、主対象は画像。
- 効果：再訪・サイト内回遊時の体感改善。初回表示には効かない。
- 手間・リスク：中。キャッシュを強くしすぎると画像差し替えの反映が遅れるため、期間は 7〜30日程度から。適用前に現行ヘッダの再確認が必要（今回の計測は経由プロキシ越しで不確実）。

### 優先5：SWELL 高速化設定の棚卸し
- 内容：SWELL 設定の高速化項目（画像の遅延読み込み、JS の遅延・最適化、キャッシュ系）が現状どうなっているかを一覧化し、未使用のものがあれば有効化を検討する。
- 効果：項目による。TTFB 自体はサーバー側（ConoHa のページキャッシュ）の影響が大きく、テーマ設定では限定的。
- 手間・リスク：中。JS 遅延はスライダーや絞り込みスクリプト（一覧ページのカスタムJS）と干渉しうるため、有効化する場合は一覧・トップの動作確認が必須。

### 参考：今後のアイキャッチ生成について
- 既存アイキャッチは変更しない方針を維持する。新規生成分は、1200×630 で 150 KB 以下を目安に圧縮率を調整すると、記事ページの総量が安定する（YESUNG の 316 KB は重めの例）。

## 除外した案

- サーバー移転・有料キャッシュプラグイン導入は、今回の範囲外として除外した。
- GA4（gtag.js）の削除・変更は計測に必要ため対象外。
